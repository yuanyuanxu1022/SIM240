# 为什么参考求解器是单核（串行）运行

记录时间：2026-11-12 02:10 CST。只读查证，未改任何设置。

## 结论

**不是"设置"成单核，是三重锁：源代码直接拒绝并行 + 冻结协议明文规定 + 启动脚本不调 mpirun。** 任何一处都足以阻止多核。

## 1. 源码级硬禁（最硬的一层）

`solver/paper1StokesReference.C:79-84`：

```cpp
#include "createMesh.H"
if (Pstream::parRun())
{
    FatalErrorInFunction << "Serial reference only: MPI is not prepared."
        << exit(FatalError);
}
```

只要检测到 MPI 并行的运行环境，求解器**立刻报错退出**，不进入物理计算。这不是性能选项，是写死的断言。

`release_manifest.json` 里 `bin/paper1StokesReference` 的 SHA 是冻结并纳入 235 项身份绑定的（`73b1f633…`），改这一行就等于改发布包，会让所有已有回执的 `executable_sha256` 失配。

## 2. 协议级规定

`PROTOCOL.md:88` 原文：

> 要求已加载 `/opt/openfoam13`，**拒其他版本和 MPI**。… **单进程，线程 1**，地址空间硬上限 4 GiB，单文件硬上限 256 MiB

另：`run_one.py` 通过 `subprocess.Popen([...paper1StokesReference...])` 直接调用可执行文件，**没有 `mpirun`、没有 `decomposePar`、没有 `nProcs` 配置**（全文搜索确认）。

## 3. 为什么要这样设计（合理推断，非文档明文）

这个求解器不是论文用的 OpenLB 主求解器，是**独立交叉验证参考**。参考值的核心要求是"任何人都能重算出同一个数"，所以：

| 理由 | 说明 |
|---|---|
| **浮点可复现性** | MPI 并行会改变全局求和的顺序，同一算例不同核数会得到末位不同的 K。参考值必须字节级可复现，否则哈希绑定（`evidence_sha256` / `native_field_sha256`）失去意义 |
| **审计性** | 每个 K 对应磁盘上的场文件 + 回执 + 指纹，任何人重算得同一数。这与"Kref 取 fine 原值而不取 Richardson 外推"是同一套逻辑（宁可选次准但查得到的，不选最准但只能信的） |
| **交叉验证的独立性** | 参考与 OpenLB 要尽量不用相同的数值路径。OpenLB 侧用 LBM 并行，FVM 侧用串行直接解法，差异归因更干净 |

⇒ **单核是"正确性成本"，不是"性能疏忽"。** 换成并行会加速，但会牺牲可复现性，等于把参考值的资格基础拆掉。

## 4. 实际代价

单线程占满 1 核 99%。本机 24 核，其余 23 核闲置。已实测的耗时：

| 算例 | 单元 | 迭代 | 墙钟 |
|---|---:|---:|---:|
| h75 P 四层 | 19200~307200 | 1~2 | 0.15 s ~ 3.95 s |
| h75 T coarse/mid | 19200/76800 | 11403/22796 | 3.4 min / 19 min |
| h75 T fine | 307200 | 65970 | **3 h 33 min** |
| h75 T tight | 307200 | 26340 | 1 h 7 min |
| h25 T fine | 184320 | 25672 | 44 min |
| h125 T fine（预估） | 454656 | 未跑 | **5~6 h** |

**P 方向（标量 Poisson）是秒级，T 方向（压速耦合 Stokes）是小时级**，差别来自方程类型与迭代次数，不是核数。

## 5. 如果确实要加速，可选项与代价

| 选项 | 能否做 | 代价 |
|---|---|---|
| 改源码开 MPI | ❌ 不能 | 破坏参考资格：哈希失配、不可复现、需重新冻结与重审全部已有回执 |
| 同时跑多个**不同**算例（各占 1 核） | ✅ 可以 | 这是唯一合法的加速方式。本机 24 核，理论上可同时跑十几个算例。但当前批次脚本是**串行**的（`run_remaining.py:139` 单循环），且协议未授权并行多算例 |
| 提高单例优先级（`nice`） | 已设 | `run_one.py` 里 `os.nice(5)` 主动降优先级，让出 CPU 给用户操作 |

**注意**：并行跑多个算例不改变任何单例的数值结果（每个仍是单进程），所以**不违反可复现性**。但它改变了"遇失败即停"的语义（一个失败时其他在飞），需要重新设计调度与停止规则，属于协议变更，需用户明确授权。
