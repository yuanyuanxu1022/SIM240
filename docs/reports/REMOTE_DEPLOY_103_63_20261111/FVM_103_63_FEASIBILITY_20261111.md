# FVM 剩余 5 点能否迁到 10.103.103.63 跑？——可行性否决报告

时间：2026-11-11 22:45–23:05（+08:00）。**只做只读核查与一个中性基准测速，未启动任何 FVM 算例、未复制算例到服务器、未改任何冻结文件。**

## 0. 结论：不建议，且有两条独立的硬拦阻

| # | 拦阻 | 性质 | 可否绕过 |
|---|---|---|---|
| 1 | **冻结释放绑定 OpenFOAM 安装本身**，103.63 的 OpenFOAM 是另一个构建 ⇒ 校验直接判 `RELEASE_DRIFT` | **科学证据链**（硬） | 需要 root 装同版本，或另立服务器版释放（治理变更） |
| 2 | **单核实测比本机慢 2.11 倍**（2.72 s vs 1.29 s） | 性能（硬） | 需 root 解除 2.25 GHz 频率上限，且解除后仍慢约 1.34 倍 |

两条叠加：**搬过去既会让证据链失效，又会变慢一倍以上。** 因此 5 个剩余点应留在本机跑。

## 1. 拦阻一：释放清单绑定了 OpenFOAM 安装的哈希

`release_manifest.json` 结构：

- `sha256`：**212 条，键为相对路径**（`PROTOCOL.md`、`bin/paper1StokesReference`、`solver/...` 等）⇒ 这部分**可移植**，换目录不影响。
- `external_sha256`：**23 条，键为绝对路径**，全部指向 `/opt/openfoam13/...` 与系统库 ⇒ 这部分**不可移植**。

校验位置：`postprocess.py:309-311`

```python
bad += [fn for fn,dg in release_data.get('external_sha256',{}).items()
        if not Path(fn).is_file() or hashlib.sha256(Path(fn).read_bytes()).hexdigest()!=dg]
if bad: return dict(status='RELEASE_DRIFT', paths=bad)
```

**实测三台机器的 OpenFOAM 哈希互不相同**：

| 文件 | 本机（清单值） | 103.63 | 102.55 |
|---|---|---|---|
| `blockMesh` | `567bd6275c8b8e96…` | `a17371f47d7038ba…` ❌ | `d46d21924b9a715a…` ❌ |
| `libOpenFOAM.so` | `bdb5746a10b6d529…` | `a565836f76534039…` ❌ | `808e148bf75d698b…` ❌ |
| `libfileFormats.so` | `35c8fe402257c336…` | `f7ed32a3588da296…` ❌ | 未测 |

⇒ **两台服务器都会立刻判 `RELEASE_DRIFT`，一个算例都跑不起来。**

好消息：系统库 `libc.so.6`、`libstdc++.so.6`、`libmpi.so.40` **三台完全一致**（`3a15d668…` / `1fd75fe7…` / `9055018b…`）。差异只出在 OpenFOAM 自身的构建产物。

**为什么不能绕过**：
- 清单里是**绝对路径** `/opt/openfoam13/...`，把本机这套 OpenFOAM 拷到别处再改路径不行——清单验的是原路径。
- 要在 103.63 上覆盖 `/opt/openfoam13`，需要 **root**。`yuanyuan` 账号**不在 sudo 组**。
- 另立「服务器版释放」＝产生第三个 `release_sha256`，按现行规则会把执行锁退回 `PENDING_ASTRA_V21_RECHECK`、抹掉 `reviewed_release_sha256`。这是治理变更，需 Astra 重新审，**不是我能单方面做的**。

## 2. 拦阻二：单核速度实测，103.63 慢 2.11 倍

**这算例是单进程串行**：`run_one.py` 全文无 `mpirun` / `decomposePar` / `-parallel`（grep 无匹配），`subprocess.Popen` 直接调 `bin/paper1StokesReference`。⇒ **128 个核对它完全无用**，只有单核性能有意义。

方法：两台各跑 OpenFOAM 自带 `incompressibleFluid/cavity`（2000 时间步，`blockMesh` + `foamRun`），每次全新副本，各 3 次。

| | 第1次 | 第2次 | 第3次 | 均值 |
|---|---:|---:|---:|---:|
| **本机** i7-13700 | 1.26 s | 1.29 s | 1.31 s | **1.287 s** |
| **103.63** EPYC 7B13 | 2.69 s | 2.72 s | 2.75 s | **2.720 s** |
| 比值 | | | | **2.11×** |

**原因（频率）**：

| | 型号 | 硬件上限 | 当前上限 | 实测运行频率 |
|---|---|---|---|---|
| 本机 | i7-13700 | 5.10 GHz | 5.10 GHz | 5.10 GHz（满速） |
| 103.63 | EPYC 7B13 | 3.54 GHz | **2.25 GHz** | 1.50 GHz |

- 103.63 的 `scaling_max_freq = 2250000`（2.25 GHz），**被限到硬件上限的 64%**，`governor = schedutil`。解除需要 root。
- 即使解除到 3.54 GHz，按比例估算约 `2.72 × 2.25/3.54 ≈ 1.73 s`，**仍比本机慢约 1.34 倍**。⇒ 不是治理问题，是硬件单核性能差距（5.1 GHz 新 Intel 核 vs 3.5 GHz Zen3 核）。

**对工期的直接含义**（按本机实测外推）：

| 层 | 本机（h75_d100_T 实测） | 若搬 103.63（×2.11） |
|---|---:|---:|
| coarse | 205 s | ≈ 7 min |
| mid | 1 144 s | ≈ 40 min |
| fine | 12 764 s（3.5 h） | ≈ 7.5 h |
| tight | 4 053 s（1.1 h） | ≈ 2.4 h |
| **单点合计** | **≈ 5.1 h** | **≈ 10.7 h** |
| **5 点合计** | **≈ 25 h** | **≈ 54 h** |

⇒ 用户原估「六点全跑约 20 多小时」是按本机算的；搬到 103.63 会变成 **50 小时以上**。

## 3. 顺带纠正一个此前口径

先前我把 102.55 上 OpenLB 1.25 nm 跑 3.5 h、本机 72 min 的差异，主要归因于「被 jj 的 Fluent 抢占」。本次中性基准显示：**服务器单核本身慢约 2 倍**也是重要因素，不能只归因于抢占。**不得再宣称「服务器更快」。**

同理，`103.63` 上已部署的 OpenLB 环境虽然身份干净、内存充足，但**单核同样慢约 2 倍**。它的价值是「不占你的电脑 / 内存够 / 长时间无人打扰」，**不是「更快」**。

## 4. 建议

**5 个剩余 FVM 点：留在本机跑。** 理由：本机单核最快、冻结释放原封不动可用、无需任何治理变更。代价是你电脑会被占用约 25 小时（单核，其余 23 核仍可用）。

若确实想让电脑轻松些，可考虑的两条路（都需要额外决定）：
1. **只把 coarse/mid 放服务器**——但同样撞 `RELEASE_DRIFT`，走不通。
2. **在 103.63 上装与本机逐字节相同的 OpenFOAM**——需要 root（`jn` 账号有 sudo 但需密码），装完哈希可对上，但速度仍慢 2.11 倍，**收益为负**，不建议。
